# ZTE Tracker Platform Audit

**Scope and evidence.** This audit began from the supplied ZIP on 2026-09-27 and was updated after the implementation work in this checkout. It is still a static source audit: no production or staging database credentials were supplied, so database state, deployed behavior, and live RLS are not asserted. The separate `zte-master-prompt.md` and the pasted transformation brief are product requirements, not repository instructions.

## Architecture

- **Current architecture:** Next.js 16 App Router, React 19, strict TypeScript, Tailwind CSS v4, Supabase Postgres/Auth, Vercel-oriented deployment, plus PWA assets. `package.json`, `next.config.ts`, `tsconfig.json`, `README.md`, and `docs/architecture.md` are the primary evidence.
- **Frontend:** 46 route files under the authenticated `(app)` feature group, shared Radix-based UI components, domain components, and SWR hooks in `src/lib/hooks`. The surface includes dashboard/daily plan, roadmap, projects, DSA/revision, goals/milestones, career/applications/interviews/resume/portfolio, skills, analytics, settings, and admin.
- **Backend:** Next route handlers for auth callback, GitHub activity, weekly email, health, and public profiles. Most authenticated data mutations and queries are browser Supabase calls through hooks, relying on RLS. Middleware refreshes the Supabase session and guards authenticated routes. `src/lib/supabase/admin.ts` creates a service-role client for server-only use; the public profile projection and weekly-summary cron are notable consumers.
- **Database:** Ordered, additive migrations in `supabase/migrations`, 83 `CREATE TABLE` statements and 137 explicit policy declarations in the source scan. Shared curriculum/catalog tables coexist with many per-user progress and career tables. Seed/content files include `data/seed.json`, `data/seed_part1.json`, snapshot JSON, and SQL seed files. Types are hand-maintained in `src/types/database.ts`.
- **Authentication:** Supabase magic-link/email OTP flow, callback exchange in `src/app/auth/callback/route.ts`, SSR browser/server clients, central middleware/session refresh, and a `handle_new_user` trigger that creates `user_settings`. README describes no password flow.
- **Authorization:** RLS is the primary user-data boundary. The original migration uses `auth.uid() = user_id` policies for core account tables; later migrations generally follow the same ownership pattern. Public profiles use an explicit service-role projection after opt-in lookup. Admin content writes use `user_settings.is_admin` via `public.is_admin()`, with self-promotion protection in 0077, draft-only content policies and release RPCs in 0084, and admin-only assignment/flag management in 0085. Live policy behavior remains unverified.

## Data model

- **Shared content:** The original roadmap remains intact. `roadmaps`/`roadmap_versions` catalog it and three versioned detailed tracks; migrations 0078–0082 hold the expanded content, 0084 adds the draft/review/test/publish lifecycle, and 0085 adds role mapping administration. Current generated content is 63 phases, 1,193 detailed topics, and 614 applied project briefs across the three detailed tracks. Existing phase/topic IDs and owner progress are preserved.
- **User-owned state:** `user_settings`, `onboarding_responses`, `user_roadmaps`, topic progress/notes/resources, project and exercise progress, DSA, daily logs, study/focus sessions, goals/milestones, career/applications/interviews, skills/evidence, financial profile, activity, quick captures, and plan/task state. RLS generally scopes rows by `user_id`.
- **Relationships and ownership:** User data commonly references `auth.users(id)` with cascading deletion and references shared phase/topic/catalog rows. Milestones relate to goals; interview rounds/attempts relate to applications/questions; progress relates to topics/projects. Public profiles and exported profile stats are explicit opt-in projections.
- **Roadmap enrollment:** `user_roadmaps` (0071) models enrollment, version, dates, weekly hours, status, and starting phase (0073/0079); a partial unique index allows at most one active enrollment per user. A trigger synchronizes active `roadmap_id` to `user_settings`. Migration 0083 commits final onboarding answers and enrollment atomically. Existing-account enrollment was intentionally not backfilled because start dates/hours were unknown.
- **Progress/projects/career:** Progress remains separate from shared topic/project definitions. Career data includes CRM, interview preparation, skills/evidence, and financial assumptions. The personalized career plan seed is a standalone SQL script (`supabase/seed_owner_career_plan.example.sql`) that explicitly targets a configured email; it is not part of normal app request handling.

## Personalization and single-user assumptions

- Identity literals occur in `supabase/seed_owner_career_plan.example.sql` (named owner email; manual seed/bootstrap path), and owner-specific salary/career assumptions are present in seed content such as `data/seed_part1.json`. These are product/data assets and migration/seed tooling, not a runtime `if (email === ...)` branch found by searching `src`.
- The owner’s original curriculum and career assumptions remain preserved. Three detailed public track families are available (frontend, Java backend/operations, and full-stack/general/data); all ten target roles currently seeded in the catalog are assigned to one of those families. Each track expands the 21-phase source curriculum and adds role-focused material. Content structure passes validation; subject-matter/editorial quality still needs a human review.
- Onboarding asks role, goal, experience, availability, date, DSA/interview readiness, and career situation. It records skills/projects notes, computes a personalized starting phase, and the final answer/enrollment write is transactional through `complete_onboarding`. Detailed roadmap screens load the active user's enrolled roadmap version and saved topic/project progress. The legacy core experience remains on its existing curriculum flow.
- `user_settings` carries a denormalized roadmap pointer and personalization/onboarding flags. Migration 0069 defaults existing rows to personalized/completed while the new-user trigger explicitly sets those flags false. The private-owner experience is therefore preserved by defaults, but a dedicated owner enrollment/private roadmap binding is not yet represented as a backfilled `user_roadmaps` record.
- No runtime hardcoded owner ID/email check was found in `src` in the sampled searches. Verify this comprehensively before implementation edits. There are hardcoded roadmap identifiers in migrations/tests and an owner-specific seed script; distinguish intended data migration/bootstrap from runtime authorization.

## Security

- **RLS:** Strong source-level pattern: core user rows use `auth.uid() = user_id`; onboarding/enrollment include own-row policies; shared catalogs expose explicit read policies. Source policies cannot prove the deployed database has all 76 migrations applied correctly. The project includes `scripts/verify-user-isolation.mjs`, but it tests representative tables only and requires live Supabase secrets.
- **Authorization/API:** GitHub route authenticates caller and reads their own username. Weekly summary requires `CRON_SECRET`, then uses service role to enumerate opted-in recipients. Health uses the service role for schema/deployment checks. Public profile API uses service role but selects a limited projection only after slug lookup and opt-in verification. Continue treating every admin-client use as privileged.
- **Cross-user risks:** Public profile page/API and OG image read another user's selected public fields using an admin/server path. These are intentional public surfaces but depend on correct opt-in lookup, slug uniqueness, and field projections. The isolation script covers settings/progress/captures/enrollment, not every user-owned table or every RPC.
- **Sensitive data:** Financial profiles, salary/application details, interview notes, career decisions, and recipient email fields are sensitive. Source migrations place these in user-scoped tables/settings; they must never enter public projections or logs. Weekly cron output currently includes per-user IDs and statuses; protect cron response logs.
- **Admin risk:** `is_admin()` is `SECURITY DEFINER`, reads `user_settings`, pins `search_path=public`, and defaults false. Migration 0077 prevents client-side self-promotion. The admin UI edits versioned phase/module/topic/project content through copied drafts and a draft → review → test → publish workflow. Role assignments, feature flags, and aggregate funnel reporting are also present in source. The migrations and live admin/non-admin protections have not been exercised against Supabase.
- **Other risks:** Cron authorization should fail closed (source does); rate limiting for public profile API is documented in-process/single-instance and therefore not a distributed abuse control. Verify environment secrets are not committed; the ZIP listing showed `.env.example` but no `.env.local` at repository root. Never expose service role client imports to client bundles.

## Multi-user risks and gaps

1. Existing users still have no guessed enrollment dates/hours; owner enrollment and continuity need a live account review before any backfill.
2. New final onboarding is transactional, but the earlier draft-save steps remain separate resumable writes.
3. The isolation script now tests detailed topic/project progress and product-event ownership in addition to core tables, but it still does not test every user-owned table or RPC; live RLS verification remains outstanding.
4. Detailed curriculum edits happen on copied drafts, with draft-only row policies and draft → review → test → publish transitions. This is source-level only until migrations are applied and admin/non-admin access is tested against staging.
5. Owner-specific content and financial assumptions remain in seed/source assets. The detailed public curricula are separate records, but the public projection and deployed RLS need a live privacy review.
6. Manual career-plan seed script matches a target email. This is setup/data migration behavior, not runtime authorization, but it remains a fragile owner-data bootstrap mechanism.

## Migration and preservation plan

1. Keep all existing migrations append-only; do not rewrite or renumber historical migrations. Snapshot current schema/data and verify migration ledger before any write migration.
2. Establish a read-only inventory of deployed user rows and the owner’s `user_settings.roadmap_id`, progress, project, career, and schedule data. Do not infer missing enrollment dates/hours.
3. Add an explicit, idempotent owner/enrollment backfill keyed to an operator-resolved auth user ID at migration execution time (never runtime email/ID behavior); preserve existing data and avoid defaulting unknown fields. Validate before and after row counts/checksums.
4. Complete an RLS inventory for every user-owned table, FK ownership chain, RPC, trigger, and service-role call. Fix policy/column privilege gaps additively, then run the two-user test plus per-table/RPC coverage against staging.
5. Detailed content is now versioned, and detailed roadmap screens resolve the caller's enrollment/version. Keep legacy IDs intact; any remapping needs an explicit mapping and rollback/export plan.
6. Three detailed roadmap families and mappings for all currently seeded roles now exist; perform subject-matter review and add new role families only when there is authored depth to support them.
7. Final onboarding/enrollment is atomic through a server-side RPC; product funnel milestones are captured with first-milestone idempotency and owner-scoped event access. Verify failure/retry behavior and actual analytics rows in staging.
8. Verify owner login and unchanged dashboard/data, two-user separation, public profile opt-in projection, backup/export, deletion, feature flags, and the content-release workflow in staging before release. Production release requires Supabase/Vercel access and a real beta cohort.

A new contract test (`tests/production-contract.test.mjs`) asserts the route fails closed on a missing `CRON_SECRET` and never returns the raw per-user array. Added `milestones`, `activity_log`, `career_decisions`, `notification_dismissals`, `study_sessions`, `weekly_commitments`, `time_blocks`, `evidence_items`, `user_skills`, `focus_sessions`, `daily_plan_task_state`, `public_streak_summary`, `exercise_progress`, `revision_history`, `roadmap_topic_notes`. Still unexecuted — needs live Supabase credentials. Remaining ~15 uncovered tables (`interview_rounds`, `interview_attempts`, `project_interview_attempts`/`questions`, `career_tracker`'s dependents, etc.) need FK fixtures that are more involved (e.g. a real `career_tracker` row to attach an `interview_rounds` row to) and were left for a follow-up pass rather than rushed.
- **CMS draft→review→test→publish workflow: audited, no bug found.** Traced the full `set_roadmap_version_status` SQL state machine in `0084_curriculum_release_workflow.sql` line by line: transition guards are monotonic with no backward path (draft→review→test→published only; re-entering draft requires a fresh `create_roadmap_draft` clone), the review-quality gate includes real cycle detection on topic prerequisites via a recursive CTE, and all 4 content tables' RLS edit policies were confirmed to require `status = 'draft'` with no exception — meaning content is genuinely frozen once it leaves draft, which closes the one scenario worth checking (validation only runs once, on draft→review entry; if content could still change afterward that would be a real gap, but it structurally cannot). Client wiring (`detailed-curriculum-editor.tsx`) doesn't trust its own `isEditable` UI flag for authorization — every write still round-trips through the RPC, which independently re-checks `is_admin()` — and RPC validation error messages propagate to the admin's toast unswallowed. This is a genuine, evidenced **negative result** (verified sound), not an unchecked item.
- **Account deletion: audited, real gap found and fixed.** `delete_own_account()` (migration `0024`) is a single `delete from auth.users where id = auth.uid()`, relying entirely on cascade for cleanup. Verified this is actually correct: grepped every `user_id ... references auth.users(id)` FK across all 85 migrations and confirmed 100% are declared `on delete cascade`, with zero exceptions (the only non-cascade FKs to `auth.users` are `created_by`/`changed_by`/`updated_by` admin-audit columns on shared curriculum tables, correctly `on delete set null` instead, since deleting an admin's account shouldn't cascade-delete content they authored). Separately, cross-checked `reset_user_progress()` (12 times patched to date, now `0086`) against every genuinely per-user table: found `financial_profiles` (salary/savings/expenses, added in migration `0052`) was never added despite being wired into the export/import backup and the Settings page's own reset-progress cache-refresh call list — meaning "Reset progress" silently left financial data behind while the UI implied a complete wipe. Fixed in new migration `0086_fix_reset_financial_profile.sql`, with a static contract test (`tests/production-contract.test.mjs`) added to pin the fix and catch the same class of gap for future tables.
- **Accessibility: static markup pass, no live screen-reader testing.** Added an optional `label` prop to the shared `Progress` component (becomes `aria-label`) since its color-tier signal (under-30%/on-track/done) was visual-only and most of its ~30 call sites across the app passed no accessible name — a screen reader would announce only a bare "N% progressbar" with no context for which metric it was. Fixed the highest-traffic 12 call sites (DSA, Skills, Dashboard stat cards, Goals, Statistics, Companies); ~18 remain (see `MASTER_GAP_MATRIX.md` for the full list) and are a mechanical follow-up using the same prop. Separately found and fixed 4 icon-only buttons in `daily-plan/plan-task-row.tsx` that relied on `title` alone (not reliably announced by assistive tech) with no `aria-label`; a broader check found most other icon-only buttons in the app already correctly use `aria-label`. No live browser/screen-reader (VoiceOver/NVDA) session was run — this was markup-level only.
